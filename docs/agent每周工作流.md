# AI Agent 每周工作流

> 本文档定义 AI Agent 执行每周任务的完整工作流程。Agent 必须严格按照本工作流执行每周任务，从生成任务清单到最终提交交付件，全流程无需人工干预。

## 二、Phase 1: 任务清单生成

### 1.1 阅览上周交付清单

**强制步骤**，必须在开始本周任务清单编写前完成。

**执行步骤**：

1. 定位上周文档目录：`docs/WeekN-1/`
2. 阅读 `WeekN-1_每日任务清单.md`，了解：
   - 上周每天的任务目标
   - 实际产出和交付物
   - 任务完成情况
3. 阅读 `WeekN-1_ReviewReport.md`，重点关注：
   - 阶段目标达成情况（已完成/未完成）
   - 遗留问题清单
   - 技术规范变更
4. 阅读其他产出文档（如有）：
   - `WeekN-1_TechResearch.md`
   - `WeekN-1_PerformanceReport.md`
   - `WeekN-1_BugFixLog.md`

**输出**：在生成的本周任务清单头部声明以下信息：

```markdown
### 前置条件

**上周交付物依赖**：
- WeekN-1_每日任务清单.md 中定义的 <具体交付物>
- WeekN-1_ReviewReport.md 中定义的 <遗留问题>

**上周遗留待解决问题**：
- <问题1>
- <问题2>

**需要延续的技术规范或架构决策**：
- <决策1>
- <决策2>
```

### 1.2 阅读策划方案

从 `docs/数字工坊_游戏策划方案与开发计划.md` 提取：

1. 当前开发阶段名称和阶段目标
2. 阶段核心功能需求（P0/P1/P2）
3. 技术栈要求
4. 关键性能指标
5. 物理参数配置

### 1.3 套用模板结构

按照 [编写每周每日任务清单要求.md](编写每周每日任务清单要求.md) 的一、二章要求搭建框架：

**必须包含的内容**：

| 章节 | 内容 |
|------|------|
| 头部元信息 | 阶段名称、时间范围、阶段目标、阶段交付物、技术栈、项目根目录 |
| 任务总览图 | 使用 ASCII 字符绘制的时间线，每天一列 |
| 每日详细任务 | Day 1 - Day N，每天的任务目标、预计工时、前置条件、详细步骤、单元测试、自验证、交付物汇总 |
| 质量验证 | 每日必须执行的质量验证命令序列 |
| Git 提交流程 | 完整的 Git 工作流步骤 |

### 1.4 按方法论推导任务内容

按照 [编写每周每日任务清单要求.md](编写每周每日任务清单要求.md) 6.3 节「从策划方案推导任务清单的方法论」生成具体任务内容：

**Step 1：提取功能模块**
- 从策划方案「核心玩法要素」表中提取所有 P0 功能
- 按技术依赖关系排序（底层→上层：渲染→物理→玩法→UI→系统）

**Step 2：映射到开发阶段**
- 概念验证期：渲染框架 + 物理引擎 + 平台适配
- 核心机制期：投放 + 合成 + 计分 + 关卡
- MVP 原型期：UI + 场景 + 完整游戏循环
- 完善期：道具 + 变形 + 天赋 + 变现

**Step 3：拆分为 Day 级任务**
- 每个功能模块按「搭建→实现→测试→文档」拆分为 1-3 天
- 确保每天有明确的交付物

**Step 4：拆分为 Step 级任务**
- 按 [编写每周每日任务清单要求.md](编写每周每日任务清单要求.md) 5.4 节「任务拆分粒度指导」拆分
- 每个 Step 标注分类（code/test/docs/research/review/config/perf/bugfix）和优先级（P0/P1/P2）

**Step 5：编排依赖与并行**
- 使用强依赖 `→` / 弱依赖 `⇢` / 并行 `∥` 标注依赖关系
- 识别可并行任务，标注 `∥`（详见 [并行执行策略](#35-并行执行策略)）

## 三、Phase 2: 任务清单复核

> **关键原则**：复核是 Agent 自主执行的核心保障，必须严格执行。复核通过后才能进入 Phase 3。

### 2.1 结构完整性检查

对照 [编写每周每日任务清单要求.md](编写每周每日任务清单要求.md) 第八章「结构完整性」检查清单逐项验证：

**头部元信息**：

- [ ] 是否包含阶段名称
- [ ] 是否包含时间范围（Day 1 - Day N）
- [ ] 是否包含阶段目标（一句话概括）
- [ ] 是否包含阶段交付物
- [ ] 是否包含技术栈
- [ ] 是否包含项目根目录绝对路径

**任务总览图**：

- [ ] 是否提供可视化时间线
- [ ] 天数与实际工作日数量一致（5-7天）
- [ ] 每天列宽统一（14字符）
- [ ] 列内容包含核心主题和辅助主题

**每日任务结构**：

- [ ] 每天是否有任务标题（`Day N — 任务主题`）
- [ ] 每天是否有基础信息表格（任务目标、预计工时、前置条件、技术栈要求）
- [ ] 每个步骤是否有可量化的交付标准（SMART原则）
- [ ] 代码示例是否完整可运行
- [ ] 是否包含单元测试任务（如适用）
- [ ] 是否包含代码审查自查清单
- [ ] 最后一天是否包含阶段评审和文档归档

**前置条件**：

- [ ] 是否已阅览上周交付清单和评审报告
- [ ] 是否明确声明上周交付物依赖
- [ ] 是否列出遗留问题

### 2.2 逐项对照检查清单验证

对照 [编写每周每日任务清单要求.md](编写每周每日任务清单要求.md) 第八章完整检查清单逐项验证：

**任务编排检查**：

- [ ] 每个 Step 是否标注了分类（code/test/docs/research/review/config/perf/bugfix）
- [ ] 每个任务是否标注了优先级（P0/P1/P2）
- [ ] P0 任务是否不超过 40%
- [ ] P0 任务是否安排在周初（Day 1-3）
- [ ] 每日总工时是否在 4-8h 范围内
- [ ] 任务依赖关系是否正确标注（强依赖 `→` / 弱依赖 `⇢` / 并行 `∥`）
- [ ] Day 目标是否可追溯到 Week 目标

**质量保障检查**：

- [ ] Git 提交信息是否符合规范（`类型: 详细描述`，50-100字符）
- [ ] 分支命名是否符合规范（`Vonxuvin/Week<N>Task`）
- [ ] 是否与策划方案中的设计保持一致
- [ ] 是否包含跨环境测试验证（微信开发者工具 + Chrome）
- [ ] 文档归档是否符合规范（`docs/WeekN/WeekN_<文档类型>.md`）
- [ ] `package.json` 依赖版本是否明确（无 `^`、`~`、`*`）
- [ ] 新增依赖是否已在 `docs/dependencies.md` 中记录

**异常处理检查**：

- [ ] 是否识别了本周关键风险
- [ ] 是否为 P0 任务预留了缓冲时间
- [ ] 是否定义了任务阻塞时的升级处理流程

### 2.3 自验证可执行性检查

对照 [编写每周每日任务清单要求.md](编写每周每日任务清单要求.md) 第九章「Agent 可执行性」检查清单逐项验证：

- [ ] 头部元信息是否包含项目根目录绝对路径
- [ ] Day 1 首步是否包含环境验证命令（`node -v`、`npm -v`、`npm install`）
- [ ] 是否包含 `mkdir -p docs/Week<N>` 创建文档目录步骤
- [ ] 所有新建文件是否提供了完整可运行的代码内容
- [ ] 所有修改文件是否提供了修改后的完整内容
- [ ] 所有命令是否可直接复制执行（无占位符）
- [ ] 是否使用 `npm run <script>` 格式引用命令
- [ ] 每天是否包含质量验证命令序列（typecheck → lint → test → coverage → build）
- [ ] 每天末尾是否包含可执行的自验证步骤
- [ ] Git 工作流是否包含完整步骤（checkout → status → add → commit → push）
- [ ] 每周最后一天是否包含完整的评审报告模板
- [ ] 每个 Step 是否预留了状态标记位和执行日志区域
- [ ] 是否包含常见失败场景的恢复步骤指引

### 2.4 复核结果判定

**复核通过条件**：

- 结构完整性检查：全部通过
- 逐项对照检查清单验证：全部通过
- 自验证可执行性检查：全部通过

**复核不通过处理**：

1. 标记未通过的检查项
2. 根据检查项修复任务清单
3. 重新执行完整复核流程
4. 直到全部通过

**输出**：复核通过后，在任务清单头部声明：

```markdown
## 复核确认

- [x] 结构完整性检查：通过
- [x] 逐项对照检查清单验证：通过
- [x] 自验证可执行性检查：通过
- [ ] **Agent 执行开始**：<复核通过时间>
```

## 四、Phase 3: 任务执行

### 3.1 环境准备与验证

**Day 1 首步必须执行**：

```bash
# 1. 验证 Node.js 版本
node -v
# 期望输出：Node.js 版本 ≥ 18.x

# 2. 验证 npm 可用
npm -v
# 期望输出：npm 版本号

# 3. 切换到项目根目录
cd .

# 4. 安装/更新依赖
npm install

# 5. 创建当周文档目录
mkdir -p docs/Week<N>
```

**环境验证失败处理**：

| 失败场景 | 处理步骤 |
|----------|----------|
| `node -v` 失败 | 报告环境问题，停止执行 |
| `npm -v` 失败 | 报告环境问题，停止执行 |
| `npm install` 失败 | 1. 检查网络连接 2. `npm cache clean --force` 3. 删除 `node_modules` 和 `package-lock.json` 后重试 4. 仍失败则标记 blocked |

### 3.2 执行每日任务

**每日任务执行循环**：

```
For each Day in [Day 1, Day 2, ..., Day N]:
    1. 更新任务状态为 in_progress
    2. 记录开始时间
    
    3. For each Step in Day.Tasks:
        a. 更新 Step 状态为 in_progress
        b. 记录执行日志
        c. 执行文件操作（创建/修改）
        d. 执行命令
        e. 验证交付标准
        f. 更新 Step 状态为 completed
        
    4. 执行质量验证命令
       npm run typecheck
       npm run lint
       npm run test
       npm run test:coverage
       npm run build
    
    5. 执行自验证步骤
       npm run dev
       浏览器访问验证
       微信开发者工具验证
    
    6. Git 提交流程
       git checkout Vonxuvin/Week<N>Task
       git status
       git add .
       git commit -m "<type>: <详细描述>"
       git push origin Vonxuvin/Week<N>Task
    
    7. 更新任务状态为 completed
    8. 记录结束时间
```

**Step 执行状态标记**：

```markdown
#### Step N.M：步骤名称 [pending / in_progress / completed / blocked]

**执行日志**：
- <时间戳>：开始执行
- <时间戳>：<关键操作及结果>
- <时间戳>：完成 / 阻塞原因
```

### 3.3 每日质量验证

**每日任务完成后必须执行**：

```bash
# 1. TypeScript 类型检查
npm run typecheck
# 必须零错误

# 2. ESLint 代码检查
npm run lint
# 必须零错误零警告

# 3. 单元测试
npm run test
# 必须全部通过

# 4. 覆盖率报告
npm run test:coverage
# 验证覆盖率 ≥ 80%

# 5. 生产构建
npm run build
# 必须成功
```

**验证失败处理**：

- 任一命令失败，修复问题后重新执行全部验证命令
- 不得跳过失败的验证步骤
- 修复超过 1h 仍未解决，标记当前任务为 `blocked`

### 3.4 自验证操作

**每个 Day 末尾执行**：

```markdown
### Day N 自验证

1. 启动开发服务器：`npm run dev`
2. 打开浏览器访问 `http://localhost:<端口号>`
3. 验证以下行为：
   - [ ] <具体可观察的行为1>
   - [ ] <具体可观察的行为2>
4. 打开微信开发者工具，导入项目目录 `.`
5. 验证以下行为：
   - [ ] <微信环境中的具体行为1>
6. 检查浏览器控制台和微信开发者工具控制台，确认无错误输出
```

### 3.5 Git 提交规范

**分支管理**：

- 每周 Day 1：从 main 分支创建 `Vonxuvin/Week<N>Task`
- 每天完成后：在该分支上提交并推送
- 禁止直接在 main 分支开发

**提交流程**：

```bash
# 每周 Day 1 首次执行
git checkout main
git pull origin main
git checkout -b Vonxuvin/Week<N>Task

# 后续 Day 切换回分支
git checkout Vonxuvin/Week<N>Task

# 每天提交
git status
git add .
git commit -m "<type>: <详细描述>"
git push origin Vonxuvin/Week<N>Task
```

**提交信息格式**（必须符合 Conventional Commits）：

```
<type>: <详细描述>
```

| 类型 | 用途 |
|------|------|
| feat | 新功能 |
| fix | 修复 |
| docs | 文档 |
| test | 测试 |
| refactor | 重构 |
| chore | 构建/工具 |

**禁止使用的模糊描述**：
- ❌ `每日任务开发`
- ❌ `修改bug`
- ❌ `更新代码`
- ❌ `WIP`
- ❌ `test`

### 3.6 并行执行策略

当任务清单中标注了并行任务（`∥` 符号）时，Agent 按以下规则执行：

**启用条件**（必须同时满足以下全部条件才可并行执行）：

1. 两个任务之间**无强依赖关系**（不存在 A 未完成则 B 无法开始的情况）
2. 两个任务操作**不同的文件或模块**（避免代码冲突）
3. 两个任务可由 AI agent **交替推进**（不要求同时进行）
4. 任务量确实需要并行才能在一周内完成

**不满足条件时禁止并行执行**，严格按顺序逐日执行。

**并行任务标注格式**（在任务清单中）：

| 并行组合 | 任务 A | 任务 B | 并行理由 |
|----------|--------|--------|----------|
| Day 19 ∥ Day 20 | 核心界面实现（UI 部分） | 关卡系统框架（数据部分） | UI 与数据逻辑无强依赖，操作不同文件 |

**并行执行流程**：

```
For each 并行组合 in 任务清单:
    1. 确认并行条件全部满足
    2. 交替推进两个任务（以 Step 为单位切换）
    3. 每个 Step 完成后记录执行日志
    4. 两个任务各自独立执行质量验证
    5. 两个任务各自独立执行 Git 提交
```

**并行执行注意事项**：

- 并行任务各自使用独立的 Git 提交，提交信息分别描述各自变更
- 并行任务的质量验证各自独立执行，互不影响
- 如并行中任一任务阻塞，另一任务继续执行，阻塞任务按 [常见失败场景处理](#六常见失败场景处理) 处理

### 3.7 依赖管理规范

在执行任务过程中涉及新增或修改依赖时，必须严格遵守以下规范：

**版本号定义**：

- `package.json` 中所有依赖必须明确定义**具体版本号**
- **禁止**使用 `^`、`~`、`*` 等模糊版本标识
- 良好示例：`"pixi.js": "8.1.0"`、`"matter-js": "0.20.0"`
- 禁止示例：`"pixi.js": "^8.0.0"`、`"matter-js": "*"`

**新增依赖评估流程**：

1. **必要性评估**：确认现有依赖无法满足需求，确需引入新依赖
2. **安全性评估**：检查依赖包是否存在已知安全漏洞（通过 `npm audit`）
3. **性能评估**：评估依赖包体积、加载性能、运行时性能影响
4. **社区活跃度评估**：优先选择 GitHub Stars ≥ 1000、最近 3 个月有更新的库
5. **维护状态评估**：确认依赖有活跃维护者，无长期未解决的 Issue

**依赖引入文档化**：

- 在 `docs/dependencies.md` 中记录所有新增依赖
- 记录格式：

  ```markdown
  | 依赖名 | 版本 | 引入日期 | 引入原因 | 替代方案 | 评估人 |
  |--------|------|----------|----------|----------|--------|
  | gsap | 3.12.2 | 2026-05-10 | UI 动画补间 | 无 | Vonxuvin |
  ```

**依赖锁定**：

- 提交 `package-lock.json` 到版本控制
- 确保团队成员使用完全一致的依赖版本

## 六、常见失败场景处理

| 失败场景 | Agent 自主处理步骤 |
|----------|-------------------|
| `npm install` 失败 | 1. 检查网络连接 2. `npm cache clean --force` 3. 删除 `node_modules` 和 `package-lock.json` 后重试 4. 仍失败则标记 blocked |
| TypeScript 编译错误 | 1. 读取错误信息定位文件和行号 2. 修复类型错误 3. 重新运行 `npm run typecheck` 4. 重复直到零错误 |
| 单元测试失败 | 1. 读取失败测试的详细信息 2. 分析是测试代码问题还是业务代码问题 3. 修复后重新运行 `npm run test` 4. 全部通过后继续 |
| Lint 错误 | 1. 运行 `npm run lint -- --fix` 尝试自动修复 2. 无法自动修复的手动修改 3. 重新运行 `npm run lint` 确认零错误 |
| 端口被占用 | 1. 查找占用进程 `npx kill-port <端口号>` 2. 或更换端口号 3. 重新启动开发服务器 |
| 文件已存在（创建冲突） | 1. 读取已存在的文件内容 2. 对比任务清单要求的完整内容 3. 如有差异则覆盖更新，如一致则跳过 |
| 覆盖率不达标 | 1. 分析未覆盖的代码路径 2. 补充测试用例 3. 重新运行覆盖率检查 4. 重复直到 ≥ 80% |
| Git 提交冲突 | 1. `git fetch origin` 2. `git merge origin/main` 解决冲突 3. `git add .` 4. `git commit -m "merge: 解决与 main 的冲突"` |
| 任务阻塞超过 2h | 1. 标记任务为 `blocked` 2. 记录阻塞原因 3. 评估是否可跳过 4. 报告阻塞情况 |
