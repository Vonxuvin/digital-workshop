# 编写每周每日任务清单要求

> 编写 `digital-workshop/docs` 中的每周每日任务清单及游戏策划方案时，必须遵守如下规范与要求。

---

## 〇、AI Agent 执行指令

本文档是 AI agent 编写每周每日任务清单的**唯一规范依据**。执行时遵循以下优先级：

0. **先阅览上周交付清单**：在编写本周任务前，必须完整阅览并理解上周的交付清单（`docs/WeekN-1/WeekN-1_每日任务清单.md`）及评审报告（`docs/WeekN-1/WeekN-1_ReviewReport.md`），充分了解前期工作成果、遗留问题及技术规范，有效避免前后工作对接中出现需求理解偏差、功能冲突或技术实现不一致等问题
1. **先读策划方案**：从 `docs/数字工坊_游戏策划方案与开发计划.md` 提取当前阶段的功能需求
2. **再套模板结构**：按 [一、文档整体结构要求](#一文档整体结构要求) 和 [二、每日任务详细结构](#二每日任务详细结构) 搭建框架
3. **按方法论推导**：使用 [6.3 从策划方案推导任务清单的方法论](#63-从策划方案推导任务清单的方法论) 生成任务内容
4. **逐项自检**：完成后对照 [八、附录：检查清单](#八附录检查清单) 逐项验证
5. **可执行性验证**：确认任务清单满足 [九、Agent 自主执行保障规范](#九agent-自主执行保障规范) 的全部要求，确保 agent 可零干预独立执行

**关键约束**：
- 所有代码示例必须完整可运行，禁止伪代码
- 所有交付标准必须可量化验证（SMART 原则）
- 所有 Git 提交信息必须符合 `类型: 详细描述` 格式，禁止模糊描述
- 所有任务必须标注分类（code/test/docs/research/review/config/perf/bugfix）和优先级（P0/P1/P2）
- 每日总工时不超过 8h，不低于 4h

## 一、文档整体结构要求

### 1.1 头部元信息

每份周任务清单必须包含以下头部信息：

| 字段    | 说明               | 示例                                                    |
| ----- | ---------------- | ----------------------------------------------------- |
| 阶段名称  | 当前开发阶段的命名        | 概念验证期 / 核心机制验证与原型完善期 / 原型开发期-MVP核心                    |
| 时间范围  | 具体的日期跨度          | Day 1 - Day 7（7个工作日）                                  |
| 阶段目标  | 一句话概括本阶段要达成的核心目标 | 验证核心玩法可行性，确认 PixiJS + Matter.js 技术方案                  |
| 阶段交付物 | 本阶段结束必须产出的成果     | 可交互的物理合成原型 + 技术调研报告 + 性能测试报告                          |
| 技术栈   | 本阶段使用的主要技术       | TypeScript / PixiJS v8 / Matter.js / Vite / 微信小游戏 API |
| 项目根目录 | 项目的绝对路径          | `.`                        |

### 1.2 任务总览图

在头部之后，必须提供一个可视化的任务总览时间线，清晰展示每天的核心主题。

**格式要求**：
- 使用 ASCII 字符绘制时间线
- 每天占一列，列宽统一（14 字符）
- 第一行显示 Day N 编号，第二行显示核心主题，第三行显示辅助主题
- 天数不固定为 7 天，根据实际工作日数量调整（5-7 天均可）

**7 天示例**：
```
Day 1          Day 2          Day 3          Day 4          Day 5          Day 6          Day 7
├──────────────┼──────────────┼──────────────┼──────────────┼──────────────┼──────────────┤
│ 项目初始化    │ 物理引擎集成  │ 微信环境搭建  │ 核心原型开发  │ 投放与合成   │ 连锁合成验证  │ 阶段评审
│ + 渲染框架   │ + 调研报告   │ + 平台适配   │ + 基础方块   │ + 碰撞检测   │ + 性能测试   │ + 文档归档
└──────────────┴──────────────┴──────────────┴──────────────┴──────────────┴──────────────┘
```

**5 天示例**：
```
Day 1          Day 2          Day 3          Day 4          Day 5
├──────────────┼──────────────┼──────────────┼──────────────┤
│ 项目初始化    │ 物理引擎集成  │ 核心原型开发  │ 投放与合成   │ 阶段评审
│ + 渲染框架   │ + 调研报告   │ + 基础方块   │ + 碰撞检测   │ + 文档归档
└──────────────┴──────────────┴──────────────┴──────────────┘
```

## 二、每日任务详细结构

每一天的任务必须按以下结构编写：

### 2.1 任务标题

格式：`Day N — 任务主题`

示例：`Day 1 — 项目初始化与渲染框架搭建`

### 2.2 基础信息表格

| 属性        | 内容                        |
| --------- | ------------------------- |
| **任务目标**  | 一句话描述当天要达成的目标             |
| **预计工时**  | 6-8 小时（或更细分为 编码Xh + 自测Xh） |
| **前置条件**  | 开始本任务前必须完成的依赖             |
| **技术栈要求** | 当天涉及的具体技术版本               |

### 2.3 详细任务步骤

每个步骤必须包含：

#### Step N.M：步骤名称

**文件操作**：需要创建/修改的文件清单

**命令**：需要执行的终端命令（如有）

**代码/配置内容**：

- 如果是新文件，提供完整的代码内容
- 如果是修改文件，提供修改后的完整内容或明确的修改点
- 配置文件提供完整的 JSON / TypeScript 配置

**交付标准**：该步骤完成后的验收条件，必须可量化、可验证

### 2.4 单元测试任务（如适用）

| 测试项   | 测试内容                      | 通过标准       |
| ----- | ------------------------- | ---------- |
| 单例测试  | 多次调用 getInstance() 返回同一实例 | 引用相等       |
| 状态机测试 | 状态切换序列正确                  | 无异常，事件正确广播 |

### 2.5 代码审查与提交

**质量验证命令**（每天必须，按顺序执行）：

```bash
npm run typecheck    # TypeScript 类型检查，必须零错误
npm run lint         # ESLint/TSLint 代码检查，必须零错误零警告
npm run test         # 运行全部单元测试，必须全部通过
npm run test:coverage  # 生成覆盖率报告，验证覆盖率 ≥ 80%
npm run build        # 生产构建，必须成功
```

**自查清单**：

- [ ] TypeScript 编译无错误（`npm run typecheck` 通过）
- [ ] Lint 检查无错误无警告（`npm run lint` 通过）
- [ ] 单元测试全部通过（`npm run test` 通过）
- [ ] 覆盖率 ≥ 80%（`npm run test:coverage` 验证）
- [ ] 功能可正常运行
- [ ] 代码注释清晰，命名规范

**Git 提交**（完整工作流）：

```bash
# Day 1 首次执行：从 main 创建本周分支
git checkout main
git pull origin main
git checkout -b Vonxuvin/Week<N>Task

# 后续 Day：切换到本周分支
git checkout Vonxuvin/Week<N>Task

# 每天提交
git status
git add .
git commit -m "feat: 实现物理引擎碰撞检测与合成触发逻辑"
git push origin Vonxuvin/Week<N>Task
```

> 提交信息格式详见 [3.4.1 提交信息格式](#341-提交信息格式)，禁止使用模糊描述。
> 完整 Git 工作流规范详见 [9.6 完整 Git 工作流](#96-完整-git-工作流)。

### 2.6 自验证步骤

每天任务清单末尾必须包含可执行的自验证步骤，agent 按步骤操作即可确认功能正确：

```markdown

   - [ ] <微信环境中的具体行为 1>
6. 检查浏览器控制台和微信开发者工具控制台，确认无错误输出
```

> 自验证规范详见 [9.5 自验证操作步骤](#95-自验证操作步骤)。

## 三、内容编写规范

### 3.1 代码规范

- 所有代码示例必须是**完整可运行**的，不能是伪代码
- TypeScript 代码需包含完整的类型定义
- 配置文件提供完整内容，便于直接复制使用
- 代码中需包含必要的注释说明关键逻辑

### 3.1.1 代码质量要求

提交代码前必须通过以下质量检查：

**代码风格检查**：

- 必须通过 ESLint / TSLint 等代码检查工具验证
- 确保代码风格一致性（缩进、引号、分号、命名规范等）
- 禁止提交包含 lint 错误的代码

**单元测试要求**：

- 核心业务逻辑必须编写单元测试
- 测试覆盖率不低于 **80%**
- 测试用例需覆盖正常流程、异常流程、边界条件
- 提交前必须运行全部测试并确保通过

**技术方案评审**：

- 复杂功能实现需提前进行技术方案评审
- 评审通过后方可开始编码
- 避免后期大规模重构
- 技术方案文档需归档到当周文档文件夹

**代码审查清单**：

- [ ] ESLint / TSLint 检查通过，无错误无警告
- [ ] 单元测试全部通过，覆盖率 ≥ 80%
- [ ] 复杂功能已通过技术方案评审
- [ ] 代码注释清晰，关键逻辑有说明
- [ ] 无冗余代码、无未使用的变量/导入
- [ ] 无 console.log 调试代码（生产环境）

### 3.2 文件路径规范

- 使用绝对路径或从项目根目录开始的相对路径
- 路径格式：`src/core/Game.ts`、`docs/Week1_TechResearch.md`

### 3.2.1 依赖管理规范

项目依赖包必须严格按照以下要求管理：

**版本号定义**：

- `package.json` 中所有依赖必须明确定义**具体版本号**
- **禁止**使用 `^`、`~`、`*` 等模糊版本标识
- 良好示例：`"pixi.js": "8.1.0"`、`"matter-js": "0.20.0"`
- 禁止示例：`"pixi.js": "^8.0.0"`、`"matter-js": "*"`

**新增依赖评估流程**：

1. **必要性评估**：确认现有依赖无法满足需求，确需引入新依赖
2. **安全性评估**：检查依赖包是否存在已知安全漏洞（通过 `npm audit`）
3. **性能评估**：评估依赖包体积、加载性能、运行时性能影响
4. **社区活跃度评估**：优先选择 GitHub Stars ≥ 1000、最近 3 个月有更新的库
5. **维护状态评估**：确认依赖有活跃维护者，无长期未解决的 Issue

**依赖引入文档化**：

- 在 `docs/dependencies.md` 中记录所有新增依赖
- 记录格式：
  ```markdown
  | 依赖名 | 版本 | 引入日期 | 引入原因 | 替代方案 | 评估人 |
  |--------|------|----------|----------|----------|--------|
  | gsap | 3.12.2 | 2026-05-10 | UI 动画补间 | 无 | Vonxuvin |
  ```

**依赖锁定**：

- 提交 `package-lock.json` 到版本控制
- 确保团队成员使用完全一致的依赖版本

### 3.3 交付标准规范

交付标准必须满足 **SMART 原则**：

- **S**pecific：具体明确，不模糊
- **M**easurable：可量化验证
- **A**chievable：在当天工期内可完成
- **R**elevant：与阶段目标相关
- **T**ime-bound：有明确完成时点

示例：

- ✅ 良好：`运行后屏幕显示 5 个彩色圆形从空中落下，圆形与地面碰撞后有弹跳效果`
- ❌ 不佳：`完成物理引擎集成`

### 3.4 Git 提交规范

#### 3.4.1 提交信息格式

采用 **Conventional Commits** 规范，格式必须为：

```
<type>: <详细描述>
```

**格式要求**：

- 必须包含 `类型: 详细描述` 的格式，如：`feat: 添加用户登录验证功能`、`fix: 修复首页轮播图加载异常问题`
- 明确说明本次修改的具体内容、涉及模块及解决的问题
- **禁止**使用模糊描述，如：`每日任务开发`、`修改bug`、`更新代码`、`做了一些调整` 等
- 提交信息长度建议控制在 **50-100 字符**
- 确保其他团队成员能快速理解变更内容

**良好示例**：

- `feat: 实现物理引擎碰撞检测与合成触发逻辑`
- `fix: 修复方块堆叠超过警戒线未触发游戏结束的问题`
- `refactor: 优化计分系统连锁倍率计算算法，提升性能30%`
- `docs: 更新Week3每日任务清单，补充Day18 UI框架搭建步骤`

**禁止示例**：

- ❌ `每日任务开发`
- ❌ `修改bug`
- ❌ `更新代码`
- ❌ `做了一些调整`
- ❌ `WIP`
- ❌ `test`

常用 type：

| 类型       | 用途    |
| -------- | ----- |
| feat     | 新功能   |
| fix      | 修复    |
| docs     | 文档    |
| test     | 测试    |
| refactor | 重构    |
| chore    | 构建/工具 |

#### 3.4.2 分支命名规范

每周分支命名格式严格遵循：

```
Vonxuvin/Week<N>Task
```

**示例**：

- `Vonxuvin/Week1Task`
- `Vonxuvin/Week2Task`
- `Vonxuvin/Week3Task`

**规则**：

- 必须以 `Vonxuvin/` 为前缀
- 周次使用数字，如 `Week1`、`Week2`
- 后缀固定为 `Task`
- 每周创建独立分支，禁止在主干分支直接开发

## 四、周与周的衔接要求

### 4.1 前置条件明确与上周成果阅览

**强制步骤**：在编写本周任务清单前，必须完成以下阅览工作：

1. **阅览上周交付清单**：完整阅读 `docs/WeekN-1/WeekN-1_每日任务清单.md`，了解上周每天的任务目标、实际产出和交付物
2. **阅览上周评审报告**：完整阅读 `docs/WeekN-1/WeekN-1_ReviewReport.md`，重点关注：
   - 阶段目标达成情况（哪些已完成、哪些未完成）
   - 遗留问题清单（技术难点、未解决的 Bug、待优化项）
   - 技术规范变更（API 变更、架构调整、配置修改）
3. **阅览上周其他产出文档**：如技术调研报告、性能测试报告、Bug 修复日志等

**阅览目的**：
- 避免需求理解偏差：确保本周任务与上周已实现功能逻辑一致
- 避免功能冲突：确保新增功能不与已有功能产生冲突或覆盖
- 避免技术实现不一致：确保沿用上周确定的技术方案、代码风格和架构模式
- 有效衔接遗留问题：将上周未解决的问题纳入本周任务规划

**前置条件声明**：完成阅览后，在本周任务清单头部明确列出：
- 需要上周哪些交付物完成才能开始
- 上周遗留的待解决问题
- 本周需要延续的技术规范或架构决策

### 4.2 并行执行策略

在满足以下**全部条件**时，可标注并行任务组合：

**启用条件**：
1. 两个任务之间**无强依赖关系**（不存在 A 未完成则 B 无法开始的情况）
2. 两个任务操作**不同的文件或模块**（避免代码冲突）
3. 两个任务可由**不同开发者**分别执行（或 AI agent 可交替推进）
4. 任务量确实需要并行才能在一周内完成

**不满足条件时禁止标注并行**，避免任务清单过于复杂导致执行混乱。

**并行任务标注格式**：

| 并行组合 | 任务 A | 任务 B | 并行理由 |
|----------|--------|--------|----------|
| Day 19 ∥ Day 20 | 核心界面实现（UI 部分） | 关卡系统框架（数据部分） | UI 与数据逻辑无强依赖，操作不同文件 |

### 4.3 周评审与报告

每周最后一天必须包含：

1. **阶段评审**：回顾本周目标达成情况
2. **问题记录**：记录遇到的技术难点和解决方案
3. **文档归档**：将本周产出整理到 `docs/WeekN/` 目录
4. **评审报告**：输出 `WeekN_ReviewReport.md`

### 4.4 跨环境测试验证

测试要求按开发阶段分层执行，避免开发早期过度投入测试环境搭建。

#### 4.4.1 开发阶段（当前阶段，每周必做）

项目处于开发迭代期，以**微信开发者工具**为主力验证环境：

**测试环境**：

| 环境 | 版本要求 | 说明 | 频率 |
|------|----------|------|------|
| 微信开发者工具 | 最新稳定版 | **主测试环境**，模拟真机运行 | **每周必做** |
| Chrome | 最新版本 | Web 端辅助验证，快速排查渲染/逻辑问题 | **每周必做** |

**测试范围**：

- 所有新增功能的按钮点击、触摸交互、数据展示等操作
- 所有相关联功能的回归测试
- 界面布局响应式表现（微信开发者工具内切换不同机型预览）
- 元素渲染完整性（无缺失、无错位、无重叠）
- 控制台错误输出检查（无报错、无警告）

**测试通过标准**：

- [ ] 功能逻辑符合需求文档描述
- [ ] 界面展示与设计稿一致
- [ ] 无明显视觉缺陷（文字错位、颜色偏差、元素溢出等）
- [ ] 无交互卡顿（触摸响应延迟 ≤ 100ms，动画流畅 ≥ 30fps）
- [ ] 控制台无错误输出
- [ ] **禁止将未经验证的低级问题提交到开发主分支**

## 五、任务编排规范

### 5.1 任务分类标准

每个任务必须归类到以下类型之一，便于 AI agent 准确理解任务性质：

| 分类 | 标识 | 说明 | 典型产出物 |
|------|------|------|-----------|
| 编码实现 | `code` | 编写/修改源代码 | `.ts`、`.tsx`、`.json` 文件 |
| 单元测试 | `test` | 编写/运行测试用例 | `.test.ts` 文件、测试报告 |
| 文档编写 | `docs` | 编写/更新项目文档 | `.md` 文件 |
| 技术调研 | `research` | 技术方案调研与评估 | 调研报告 `.md` |
| 代码审查 | `review` | 代码自查与评审 | 审查清单、评审记录 |
| 环境配置 | `config` | 工程/构建/部署配置 | `tsconfig.json`、`vite.config.ts` 等 |
| 性能优化 | `perf` | 性能测试与优化 | 性能报告、优化记录 |
| 缺陷修复 | `bugfix` | 修复已发现的 Bug | Bug 修复日志 |

**使用规则**：
- 每个 Step 必须标注其分类
- 一个 Day 内应包含多种分类的任务，避免单一类型
- 每日任务中 `code` 类占比建议 50%-60%，`test` 类占比 15%-20%，其余为 `docs`/`review`/`config`

### 5.2 优先级设定原则

任务优先级分为三级，AI agent 必须按以下标准判定：

| 优先级 | 标识 | 判定标准 | 示例 |
|--------|------|----------|------|
| **P0（必须）** | `P0` | 核心玩法功能，缺失则游戏不可玩；阻塞后续任务的前置依赖 | 物理引擎集成、方块投放系统、合成逻辑 |
| **P1（重要）** | `P1` | 提升游戏体验的关键功能；影响可玩性但不阻塞核心流程 | UI 动画、音效系统、道具系统、关卡配置 |
| **P2（可选）** | `P2` | 锦上添花的功能；可在 MVP 后迭代 | 皮肤系统、排行榜、社交分享 |

**优先级分配规则**：
- 每周 P0 任务不超过 **40%**（保证可完成）
- P0 任务必须安排在周初（Day 1-3），预留缓冲时间
- P2 任务仅在 P0/P1 全部完成后才启动
- 如果 P0 任务延期，P2 任务自动顺延至下周

### 5.3 时间分配建议

每日 8 小时工时的标准分配比例：

| 活动 | 占比 | 时长 | 说明 |
|------|------|------|------|
| 编码实现 | 50% | 4h | 编写功能代码 |
| 单元测试 | 20% | 1.5h | 编写和运行测试 |
| 自测验证 | 15% | 1.2h | 手动功能验证、浏览器测试 |
| 文档更新 | 10% | 0.8h | 更新任务清单、技术文档 |
| 代码审查 | 5% | 0.5h | 自查清单、Git 提交 |

**工时估算规则**：
- 新文件创建：按文件复杂度估算，简单文件 0.5h，中等 1-2h，复杂 3-4h
- 文件修改：按修改行数估算，每 50 行约 0.5h
- 单元测试：约为对应功能编码工时的 30%-50%
- 调试修复：预留编码工时的 20% 作为缓冲

### 5.4 任务拆分粒度指导

**Step 拆分标准**：

| 粒度 | 适用场景 | 示例 |
|------|----------|------|
| 粗粒度（1个Step=2-3h） | 简单配置、工具类实现 | Step 1.3：建立项目目录结构 |
| 中粒度（1个Step=1-2h） | 单一功能模块实现 | Step 2.1：物理引擎管理器实现 |
| 细粒度（1个Step=0.5-1h） | 复杂功能需分步说明 | Step 3.1：微信小游戏配置文件 |

**拆分原则**：
- 一个 Step 只做**一件事**（单一职责）
- 一个 Step 的产出物应**可独立验证**
- 如果一个 Step 超过 3h，必须拆分为多个子 Step
- 每个 Day 包含 3-6 个 Step 为宜

### 5.5 任务依赖关系表达

**依赖类型**：

| 类型 | 符号 | 说明 | 示例 |
|------|------|------|------|
| 强依赖 | `→` | A 未完成则 B 无法开始 | Day 1 → Day 2 |
| 弱依赖 | `⇢` | A 未完成 B 可部分进行 | Day 3 ⇢ Day 4 |
| 并行 | `∥` | A 和 B 可同时进行 | Day 19 ∥ Day 20 |

**表达格式**（在每个 Day 的「前置条件」中）：
```
### 前置条件
- Day N-1 全部完成（强依赖）
- Week N-1 核心原型已验证通过（强依赖）
- Day N-2 UI 框架可部分并行（弱依赖）
```

### 5.6 任务状态跟踪

每个任务必须使用以下状态标记：

| 状态 | 标识 | 说明 |
|------|------|------|
| 待开始 | `pending` | 前置条件未满足 |
| 进行中 | `in_progress` | 当前正在执行 |
| 已完成 | `completed` | 已通过验收标准 |
| 已阻塞 | `blocked` | 遇到无法自行解决的问题 |
| 已取消 | `cancelled` | 经评审确认不再需要 |

**阻塞处理流程**：
1. 标记任务为 `blocked`，记录阻塞原因
2. 评估是否可跳过该任务继续后续工作
3. 如不可跳过，启动备用方案或升级处理
4. 阻塞超过 2h 必须记录到当日开发日志

### 5.7 异常处理与风险应对

**常见异常场景及应对**：

| 异常场景 | 应对策略 |
|----------|----------|
| 任务无法在当日完成 | 标记未完成部分，顺延至次日首项任务；调整后续 P2 任务优先级 |
| 技术方案不可行 | 立即停止编码，记录问题，启动替代方案调研 |
| 依赖的第三方库有 Bug | 评估影响范围，寻找 workaround 或替代库 |
| 性能不达标 | 记录性能数据，分析瓶颈，优先优化而非继续堆功能 |
| 前置任务延期 | 评估是否可弱依赖方式并行推进，调整本周任务优先级 |

**风险记录格式**：
```markdown
| 风险 | 等级（高/中/低） | 影响范围 | 应对措施 | 状态 |
|------|------------------|----------|----------|------|
| Matter.js 性能瓶颈 | 中 | Day 5-6 连锁合成 | 降低同屏方块数上限 | 监控中 |
```

### 5.8 任务清单评审流程

任务清单编写完成后，必须经过以下评审：

1. **自评审**（编写者）：对照 [八、附录：检查清单](#八附录检查清单) 逐项自查
2. **逻辑验证**：确认 Day 之间依赖关系正确，无循环依赖
3. **工时校验**：每日总工时不超过 8h，不低于 4h
4. **覆盖率检查**：确认所有 P0 策划需求均有对应任务

- MVP 原型期：UI + 场景 + 完整游戏循环
- 完善期：道具 + 变形 + 天赋 + 变现

**Step 3：拆分为 Day 级任务**
- 每个功能模块按「搭建→实现→测试→文档」拆分为 1-3 天
- 确保每天有明确的交付物

**Step 4：拆分为 Step 级任务**
- 按 [5.4 任务拆分粒度指导](#54-任务拆分粒度指导) 拆分
- 每个 Step 标注分类和优先级

**Step 5：编排依赖与并行**

- 识别可并行任务，标注 `∥`

```
│

│   ├── 任务目标（Day 级别，服务于 Week 目标）
│   ├── Step 1.1 → 交付物 A
│   ├── Step 1.2 → 交付物 B
│   └── Day 1 交付物汇总
│

│
└── Day 7（评审日）
    ├── 阶段评审
    ├── 文档归档
    └── 评审报告
```

**层级规则**：
- Day 目标必须可追溯到 Week 目标（每个 Day 目标服务于 Week 目标的某个子目标）
- Day 交付物累积 = Week 交付物
- 如果某 Day 的交付物与 Week 目标无关，则该 Day 任务不应存在

## 九、Agent 自主执行保障规范

为确保 AI agent 能依据任务清单**独立完成当周所有工作，无需人为干预**，任务清单必须满足以下可执行性要求。

### 9.1 环境准备与验证（Day 1 首步，必须）

每周任务清单的 Day 1 第一个 Step 必须包含环境验证步骤，确保 agent 在正确的环境中执行：

**必须包含的命令**：

```bash
node -v          # 验证 Node.js 版本 ≥ 18.x
npm -v           # 验证 npm 可用
cd <项目根目录>   # 切换到项目根目录（必须使用绝对路径）
npm install      # 安装/更新依赖（每次开始新周任务必须执行）
```

**项目根目录声明**：任务清单头部元信息中必须声明项目根目录的绝对路径，所有后续命令均基于此路径执行。

**环境验证失败处理**：如果 `node -v` 或 `npm -v` 失败，agent 应停止执行并报告环境问题，不得跳过。

### 9.2 文件操作规范

任务清单中的文件操作必须满足以下要求，确保 agent 可无歧义执行：

**新建文件**：
- 必须提供**完整的文件内容**（不是描述、不是伪代码）
- 必须指定文件的**完整相对路径**（从项目根目录起）
- 代码中的 import 路径必须与实际目录结构一致

**修改已有文件**：
- 必须提供**修改后的完整文件内容**（而非仅描述修改点）
- 如果文件较大，至少提供修改涉及的完整函数/类/配置块
- 必须标注修改前后的关键差异，便于 agent 理解变更意图

**删除文件**：
- 必须明确列出要删除的文件路径
- 必须说明删除原因（重构、废弃、合并等）

### 9.3 命令执行规范

任务清单中的每个命令必须满足以下要求：

**命令完整性**：
- 所有命令必须是**可直接复制执行的完整命令**，不含占位符
- 涉及路径的命令必须使用**绝对路径或从项目根目录起的相对路径**
- 命令执行前必须声明**当前工作目录**（`cd` 到正确目录）

**标准化 scripts 要求**：

项目 `package.json` 必须包含以下标准化 scripts，任务清单中的命令统一使用这些 scripts：

```json
{
  "scripts": {
    "dev": "<启动开发服务器命令>",
    "build": "<构建命令>",
    "test": "<运行测试命令>",
    "test:coverage": "<运行测试并生成覆盖率报告>",
    "lint": "<运行代码检查命令>",
    "typecheck": "<运行类型检查命令>"
  }
}
```

任务清单中引用命令时必须使用 `npm run <script>` 格式，不得使用底层工具命令（如直接用 `vitest` 而非 `npm run test`）。

**命令执行顺序**：每个 Step 中的命令必须按执行顺序排列，agent 按顺序执行。

### 9.4 质量验证命令（每日必须）

每天任务完成后，agent 必须执行以下验证命令序列，任务清单中必须包含这些步骤：

```bash
npm run typecheck    # TypeScript 类型检查，必须零错误
npm run lint         # ESLint/TSLint 代码检查，必须零错误零警告
npm run test         # 运行全部单元测试，必须全部通过
npm run test:coverage  # 生成覆盖率报告，验证覆盖率 ≥ 80%
npm run build        # 生产构建，必须成功（如项目有构建步骤）
```

**验证失败处理**：
- 任一命令失败，agent 必须修复问题后重新执行全部验证命令
- 不得跳过失败的验证步骤直接进入下一任务
- 修复过程超过 1h 仍未解决，标记当前任务为 `blocked`，记录问题

### 9.6 完整 Git 工作流

任务清单中每个 Day 的 Git 提交流程必须包含完整步骤，agent 按序执行：

```bash
# 1. 同步远程最新代码（每次开始工作前必须执行）
git fetch origin
git pull origin main   # 同步 main 分支最新代码

# 2. 确认当前在正确分支（每周首次执行时创建分支）
git checkout -b Vonxuvin/Week<N>Task   # 每周 Day 1 首次执行
# 或
git checkout Vonxuvin/Week<N>Task      # 后续 Day 切换回分支
git pull origin Vonxuvin/Week<N>Task   # 同步本周分支最新代码

# 3. 查看变更状态
git status

# 4. 暂存变更
git add .

# 5. 提交（提交信息必须符合 3.4.1 规范）
git commit -m "<type>: <详细描述>"

# 6. 推送到远程
git push origin Vonxuvin/Week<N>Task
```

**分支管理规则**：
- 每次开始新任务前必须先执行 `git pull origin main` 同步远程最新代码
- 切换到本周分支后必须执行 `git pull origin Vonxuvin/Week<N>Task` 同步分支最新代码
- 每周 Day 1 第一步：从 main 分支创建本周分支 `Vonxuvin/Week<N>Task`
- 每天完成后：在该分支上提交并推送
- 每周最后一天：确保所有代码已推送到远程
- 禁止直接在 main 分支上开发或提交

**冲突处理**：
- 如果 pull 过程中出现冲突，先分析冲突内容
- 与本周任务相关的冲突：保留自己的修改，协商解决
- 与本周任务无关的冲突：优先保留远程版本
- 冲突解决后重新提交推送

### 9.10 常见失败场景的恢复步骤

任务清单中必须包含以下常见失败场景的处理指引：

| 失败场景 | agent 自主处理步骤 |
|----------|-------------------|
| `npm install` 失败 | 1. 检查网络连接 2. 清除缓存 `npm cache clean --force` 3. 删除 `node_modules` 和 `package-lock.json` 后重试 4. 仍失败则标记 blocked |
| TypeScript 编译错误 | 1. 读取错误信息定位文件和行号 2. 修复类型错误 3. 重新运行 `npm run typecheck` 4. 重复直到零错误 |
| 单元测试失败 | 1. 读取失败测试的详细信息 2. 分析是测试代码问题还是业务代码问题 3. 修复后重新运行 `npm run test` 4. 全部通过后继续 |
| Lint 错误 | 1. 运行 `npm run lint -- --fix` 尝试自动修复 2. 无法自动修复的手动修改 3. 重新运行 `npm run lint` 确认零错误 |
| 端口被占用 | 1. 查找占用进程 `npx kill-port <端口号>` 2. 或更换端口号 3. 重新启动开发服务器 |
| 文件已存在（创建冲突） | 1. 读取已存在的文件内容 2. 对比任务清单要求的完整内容 3. 如有差异则覆盖更新，如一致则跳过 |
